# Browslium international website

Static public website for `browslium.com`, written as seven independent language editions: English, Español, Русский, ייִדיש, עברית, Português (Brasil) and Français. Each edition has a homepage, image and video explainers, Privacy, Terms and Support.

The published root contains generated HTML for every locale and the source in `src/`. Only `/` automatically routes visitors: a saved manual language choice takes precedence over `navigator.languages`, and English is the fallback. The redirect retains the URL query and fragment. Every localized URL renders complete HTML without JavaScript and never redirects by language. The locale switcher saves an explicit preference in local storage. The root remains a crawlable language selector when JavaScript is unavailable; localized canonicals, reciprocal `hreflang`, and sitemap entries remain intact.

The language gateway and all seven homepages link to the client pilot at `https://app.browslium.com/login`; the localized homepages and every header link to the authenticated setup screen at `/setup`. “Add Device” is the sole strong hero action and still carries the visible pilot-access notice. These are navigation links, not a claim of public registration or working device enrollment. Keep the pilot-access notice visible until the CPU registration and each device path have been verified and intentionally opened.

On image and video explainers, “Add Device” is the strong action with the same pilot notice. “Explore interactive levels” and links between media sections are secondary navigation. Gallery examples illustrate project tests and do not imply that a filtering level is active on the visitor's device.

The public header defaults to “Sign In”. `assets/site.js` can display “Dashboard” only after a credentialed session check returns HTTP 200 with exactly `{"authenticated":true}` from an owner-confirmed endpoint on `https://app.browslium.com`. It restores both desktop and mobile links to Sign In before every check and when the page is hidden, then rechecks on focus, visibility return, and `pageshow`. Network errors, malformed or extra response fields, and obsolete overlapping responses leave Sign In in place. The Dashboard destination comes from the confirmed build setting, never from the status response; local storage is used only for language choice.

The candidate contract tested only in an isolated browser/CPU harness is `GET https://app.browslium.com/api/v1/client/v1/auth/session-status` with `credentials:'include'`, `mode:'cors'`, and `cache:'no-store'`. It should return only `{"authenticated":true}` or `{"authenticated":false}` for the current client cookie, no token or account data, non-cacheable headers, and credentialed CORS for the exact origin `https://browslium.com` (including `Vary: Origin`), while rejecting other origins. The candidate Dashboard destination is `https://app.browslium.com/dashboard`, which reached an authenticated `/account` page in that isolated harness. This is not production verification. Before setting `verifiedSessionEndpoint` and `verifiedDashboardUrl` in `src/build.mjs`, verify the deployed endpoint and CORS policy with a real session, then open the public site in a new tab, observe the true status response, click Dashboard, and reach the authenticated portal page. Confirm logout, revocation, expiry, and focus/visibility return in the live flow. Both constants remain empty now, so no session request is emitted and Sign In remains visible.

The shared newsletter panel is a visual placeholder. The owner chose to keep its email field and button disabled for this release; they collect and send nothing. Enable them only with a working subscription endpoint or provider form, a reviewed privacy notice, clear opt-in consent, double opt-in confirmation, and unsubscribe handling. No provider key belongs in public JavaScript. The footer uses the owner's white wordmark, changing to emerald on hover, below the lighter donation/newsletter closing area.

## Rebuild

Run `npm run build`, then `npm run qa`. No npm dependencies are required for those commands. The optional `npm run qa:browser` uses Playwright and local Chrome to test the generated desktop and mobile session links. It serves `dist/` on loopback, adds the candidate session attributes only to an in-memory HTML response, and stubs the portal endpoint; it never contacts production. The generator writes `dist/`, which can be published at the repository root on GitHub Pages. It includes `CNAME`, `.nojekyll`, `robots.txt`, `sitemap.xml` and the HTML file used to verify ownership in Google Search Console. Keep that file at the published root during future deployments. Generated pages include content-hash versions of the CSS and JavaScript URLs so browsers load each site's matching design and behavior after publication.

## Editorial accuracy

Visible text passes through intact: Browslium does not semantically analyze or filter it, even when GPU processing is active. The Text illustration is explicitly a future concept; no current text filtering is promised. It shows a landscape tablet with a black camera in the bezel and one flowing column of paragraphs with wider side margins, clipped naturally at the screen edge. Two whole sentences are replaced character by character with asterisks, including punctuation while retaining spaces. A phone shows a white blog page containing a generated street photograph with chalk-style text on a storefront sign. Two solid purple patches cover complete phrases within that photographic sign. The Audio illustration uses a purple waveform with two red-outlined muted regions, clear mute symbols, and distinct green and blue labels below arrows pointing to the regions; audio filtering remains in development. The first hero comparison uses a larger left-cropped image pair with a thin green backing accent. The home metadata and the link from the video example also name these as future concepts. The current text rule is stated on all seven homepages, their image/video explainers and the relevant FAQs; keep it consistent when editing translations.

Image policies 1–7 and video policies 1–6 follow the project owner's policy document. They describe filtering behavior; the website does not claim that all levels are live. At the owner's request, all four platform cards use a green localized “Compatible” badge as production-facing design copy; the visible pilot-access notice and feature-specific caveats remain. This badge is a presentation choice, not independent verification of a general release. Verify each platform's release before removing the pilot notice or making stronger availability claims. The informational website's Privacy Policy and Terms are separate from the product privacy notice and a future service agreement. The product notice is available in English at `/en/product-privacy/` and Spanish at `/es/product-privacy/`; the other five editions link to English. Review it against the deployed product before enabling general registration, including feature-specific processing and retention. Registration acknowledgment must be separate from optional consent. Publishing the notice does not establish that any portal feature is live.

App Store Connect currently points to `https://browslium.com/privacy`. The generated `/privacy/` route serves the same English product privacy notice as `/en/product-privacy/`; keep the English route canonical and do not add the alias to the sitemap. This route resolves the link only; the notice still needs a product-data review before an App Store submission.

The Stripe button links to a one-time voluntary contribution page. Do not add a recurring option or tax-deductibility claim without verification.

The homepage and the image/video explainers share two interactive galleries based on the owner-approved SAM 3.1 tests: three original photos plus seven results per photo, and three original silent clips plus six policy choices per clip. The photo comparison has a keyboard-accessible draggable divider. Video choices switch one player between the original and the filtered result; only the selected clip loads metadata on arrival. The localized full-block clips come from the seven official language versions in `Archive.zip`. The first second is removed from the couple clip and its levels 1–4; levels 5–6 use the complete branded block clip. These are controlled tests, not evidence of general production availability.

`python3 scripts/prepare_media.py PHOTO_GALLERY VIDEO_GALLERY BRAND_ARCHIVE` rebuilds the 68 compressed web assets from the immutable source galleries. It scales photos to 1600 px WebP and videos to at most 1280 px H.264 with fast-start metadata. It does not rerun SAM 3.1 or change the approved masks. The resulting `assets/media/manifest.json` records file sizes and SHA-256 checksums. The published assets total about 19 MiB, while only the selected video is requested by the browser.

## Search intent and international SEO

The site follows the useful parts of *How to Get to the Top of Google* (2025 Kindle edition): one coherent domain, clear page hierarchy, search-intent-specific content, descriptive titles and headings, natural internal links, mobile-readable design, useful FAQs, lightweight media, and crawlable HTML. The book's predictions about algorithms and ranking factors are not treated as verified facts. No reviews, case studies or performance figures have been invented.

Each language has a homepage plus separate image and video explainers. The research was conducted separately in Chrome search results for each locale. Broad terms observed include `content filtering` / `internet filter` (English), `filtro de contenido` / `filtrado de imágenes` (Spanish), `фильтрация контента` / `фильтр нежелательного контента` (Russian), `סינון תוכן` / `סינון תמונות` (Hebrew), `אינטערנעט פילטער` (Yiddish), `filtro de conteúdo` / `filtro de vídeos` (Brazilian Portuguese), and `filtrage de contenu` / `filtrage des images` (French). Yiddish search results are sparse; wording was kept idiomatic and avoids treating Hebrew results as Yiddish evidence. “Image filter” searches also return photo-editing tools in several languages, so page copy explicitly explains the content-protection purpose.

Every edition has its own self-canonical, reciprocal `hreflang`, localized metadata and structured WebPage data. The sitemap includes the seven language editions plus two product-notice translations. The JavaScript language prompt does not redirect or gate crawlers. Homepage FAQs are visible in HTML; no FAQ rich-result claim or unsupported FAQPage schema is made. Future search work should use Search Console query data and actual user feedback to refine wording rather than add near-duplicate keyword pages.

The four owner-confirmed social profiles (X, Instagram, YouTube and TikTok) appear in every localized footer and in the Organization `sameAs` data embedded with each WebPage. The profiles are linked as the brand's public identity; this markup makes no promise of a search feature. The local QA checks those links, the JSON-LD, sitemap alternates and the language gateway as well as the localized pages.

The owner-provided transparent white wordmark appears in the header and by default in the footer; the footer swaps to the emerald wordmark on hover. The hostname root and every locale declare the same 64 px/ICO brand favicon. Search engines may need another crawl before their result icon changes. Android, Apple/macOS, X, Instagram, YouTube and TikTok vector marks come from [Simple Icons](https://simpleicons.org/) (CC0 vector artwork, subject to each brand's trademark rules); the Windows vector and the mute symbol in the Audio illustration come from [Bootstrap Icons](https://icons.getbootstrap.com/icons/volume-mute-fill/) (MIT). The Yiddish language selector uses a komets-alef glyph rather than a national flag. The Text and Audio illustrations are original inline SVG built for this site; the street-sign photograph inside the phone is a generated project asset. Their device outlines follow the proportions of Apple's iPhone 17 Pro (71.9 × 150.0 mm) and 11-inch iPad Pro M5 in landscape (249.7 × 177.5 mm).
